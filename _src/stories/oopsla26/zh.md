# Automated Debugging of Datalog Programs

（Datalog 和 SBFL 分别是什么，这里就不介绍了——论文 Section 2 讲得蛮好懂的。至于我为什么这么贴心地指引大家去看论文，~~是因为我懒~~是出于对读者时间的尊重）

## 导读

这篇论文最大的 Contribution 在于把 Datalog 和 SBFL (Spectrum-Based Fault Localization) 联系起来：Datalog 中的 output fact 对应 SBFL 中的 test-case，其 proof tree 则对应 SBFL 中的 spectrum。一旦建立起这种联系，SBFL 就可以很自然地用到 Datalog 的自动故障定位中。但它并不是显而易见的：大家已经习惯把 SBFL 用在 Imperative Program 上，很难想到它还能用在 Datalog 这种 Declarative Program 上。

此外，论文标题里用的是 Debugging 而非 Fault Localization，这是有意为之：Datalog 先前关于故障定位的工作通常都用了 Debugging，沿用这个名字，是为了让读者更容易把这篇论文和之前的工作联系起来。但如果细究的话，这篇论文做的其实更接近 Fault Localization。Fault Localization 通常是在观察到 failure 之后，找出引发 failure 的 Program element，而 Debugging 更偏向于观测程序的运行过程，不一定要有 failure。

## 幕后故事

这篇工作的 idea 来源于左志强老师——他曾经既做过 Datalog 也做过 SBFL，能想到把这两者联系起来并不奇怪。这篇工作的初稿在 2021 年左右成型，但一直缺少真实的 Datalog Bug Benchmark，没法做比较扎实的 Evaluation。后来左老师转去做其它工作，这个工作便交给了与他长期合作的钮鑫涛老师。

为了把这个工作做出来，钮老师决定用 Doop 项目构建一个真实的 Datalog 故障 Benchmark，而这过程颇有些一波三折：一开始，任务交给了计算机系的一位硕士生，但他没有做成；后来钮老师来到苏州校区的智能软件与工程学院，任务又落到了一个本科生大创团队手里。团队最初还有其他几位同学，但到 2025 年重启时他们已经退出，这里就不一一提及了；坚持到最后、把 benchmark 做出来的是卫佳申和骆葆源——这篇论文的两位第一作者。下面是卫佳申同学的回忆：

> 这项工作背后的故事，可以从 2023 年 11 月的一次大创说起。当时钮老师把他在 2021 年与左老师合作时的一个 idea 交给我们：从 Doop 的历史版本中构建 Datalog 故障基准，并在这个基准上验证我们的自动故障定位方法。那也是我们第一次接触 Datalog，第一次了解 Doop 和 Soufflé。
>
> 这个目标听起来似乎很简明直了，只需要解决两个核心问题：第一，回退 Doop 历史版本，得到对应版本的 Datalog 文件；第二，让 Soufflé 在运行时输出我们方法所需要的信息。也正是这两个问题，几乎贯穿了整个项目。
>
> 一开始的进展并不顺利，我们连最新版 Doop 的构建都失败了，最后发现是 `build.gradle` 中某处依赖的链接需要更新。这个小问题也埋下了伏笔：后续回退历史版本时，依赖问题也会反复出现。最初我们人工从 Doop 2019—2024 的 commit 中挑出修改幅度较大的版本，希望从中捕获 bug；同时修改适配 Doop 的 Soufflé 2.0.2 的解释器模式，让它输出运行时信息。但现实并不符合我们的预期，到 2024 年 12 月大创结束时，我们甚至没有构建出一个真实 bug 实例。Doop 的大量 commit 无法成功构建；成功构建的版本多集中在 2021 年及之后，而它们之间的 Datalog 文件变化很小；零星的早期版本又因跨度太大，人工分析几乎无效。Soufflé 的运行同样困难：修改后的 Soufflé 需要记录证明树，一开始的思路是修改 Soufflé 运行时，深入它构建出的语法树节点进行魔改，让 Soufflé 一边运行一边输出中间数据用于数据分析，付出了许多努力但是成效有限，并且在大型 Datalog 程序上内存开销巨大，解释器模式几乎无法运行；早期 Doop 的 Datalog 语法也不兼容 Soufflé 2.0.2，Soufflé 会报出大量错误。最终，我们只能在 toy Datalog 程序上初步验证方法。
>
> 此后近一年时间里，项目因学业等原因停滞。一直到 2025 年 9 月，我们决定重启这项工作，重新攻克这两个核心问题。
>
> 首先是 Doop 回退。我们重新整理了自 2017 年起更完整的 commit 集合，逐一解决构建失败。大多数问题来自找不到依赖，于是我们下载依赖到本地缓存，并在回退时自动修改build.gradle实现从本地缓存读取。有些版本则是存在 doop 自定义的依赖包名，有些干脆直接是源码有小错误或兼容问题，我们也一一做了自动化修复。运行方面，Doop 在线运行会持续调用线上仓库，服务器会由于网络问题导致超时，我们改为在实体机上生成 Datalog 文件后自动推送到服务器，并记录超时 commit。经过反复试错，到 2025 年 11 月，我们终于获得所有筛选 commit 对应的 Datalog 文件。
>
> 其次是 Soufflé。基于之前的教训，我们直接锁定 Soufflé 1.5.1——这是 Doop 刚支持 Soufflé 时适配的版本。我们先把构建系统从 automake 迁移到 CMake，方便调试；然后聚焦编译器模式。编译器模式不仅运行成本远低于解释器模式，而且允许我们直接操作编译产生的中间 C++ 文件，极大减少了修改原版 Soufflé 语法树逻辑和调试它的负担。Soufflé 1.5.1 版本较早，其编译器优化并不完善。一方面，这使 C++ 结构更一致，便于自动捕获插桩位置；另一方面，相似 Datalog 规则有时被优化、有时没有，也增加了插桩的复杂性。除了一些自适应的插桩操作外，我们做了两个关键处理，其一是去除 `.plan` 语句，避免同一条规则生成多个 C++ 语句；其二是标注元素类型，便于后续成功对齐不同版本的输出元组。到 2025 年 12 月，我们基本解决该问题并开始构建 benchmark。通过比较筛选后的相对相邻版本的 Datalog，人工识别 bug，最终确定 37 个唯一 bug。
>
> 但 2025 年 12 月底，新的问题出现：旧版 Doop 运行依赖的在线仓库停止维护，不可访问了。此时我们虽已人工分析出 bug，但比较是基于一段跨度的 commit，尚未拿到精确修复该 bug 的 commit 对应的 Datalog 文件。于是我们用脚本扫描 Doop 源码，模拟 Doop 逻辑生成对应版本所需配置的 datalog 文件。尽管 Doop 源码随时间变化很大，我们还是根据不同时期的典型特征，成功复原了不同版本所需三种配置的 Datalog 文件。

至此，当年卡住这篇论文的 Benchmark，终于齐了。虽然我很早就知道这个工作，但前面那一程是构建 Benchmark 这种工程活，我实在帮不上忙；直到 2026 年 1 月论文进入写作阶段，我才参与进来。由于组里的学生大多是本科生和硕士生，写作经验有限，钮老师便让我来搭把手。我读了初稿，发现背景介绍并不好懂，Approach 部分也缺少直觉（我是一个很需要直觉引导的人），于是便打算按我的方式来重写整篇论文。

首先，为了让论文易懂，我尽量少用术语，比如全程没有引入 tuples、EDB/IDB 这些概念。在写 Approach 的时候，我想尝试给读者一个直觉：为什么 SBFL 这个为 Imperative Program 设计的方法，可以顺理成章地用到 Datalog 这种 Declarative Program 上。在思考这个问题的过程中，我提出了一个很大胆的 claim：SBFL 甚至可能更适合 Datalog。这个 claim 没什么严格论证，也没有实证支持，但直觉上是站得住脚的，于是我把它写进了 Approach。

写到 Predicate 定位方法的时候，我发现其中一个 component 似乎不太成立，于是提议做了个消融实验，结果它确实没什么用。论文在这里停滞了一阵，直到钮老师决定不再拖下去：就按目前的 Approach 把论文收完，接下来就是投稿了。这一段还是由卫佳申同学来讲：

> 投稿过程同样一波三折。我们最初计划投 ISSTA，但临近 2026 年 1 月投稿时，论文尚未完成，部分设计仍有漏洞，于是决定改投截止日期在 2026 年 3 月的 OOPSLA。这期间我们进一步完善基准和方法，但评估运行成本很大，截止前仍只得到一次评估数据。原本我们设想谓词级定位结合均值和方差排序，但实验发现方差对准确率没有增益，不符合最初的预期，多次尝试也没有找到更好的组合，最终只采用可疑值均值进行谓词级定位。反复修改后，我们提交了初稿。
>

p.s. 这里说的"方差"，就是前面消融实验决定去掉的那个 component。它没有出现在最终的论文里——所以如果你去翻论文，找不到它是正常的。

5 月 20 号，审稿意见回来了：三位审稿人中，两位持正面态度，一位持负面态度。持负面意见的审稿人对我们的方法似乎有些误解——现在想来，可能也不能全怪他：PL 圈子的学者大多不太熟悉 SBFL 这类偏软件工程的技术，而我们背景部分的铺垫大概也不够。总的来说，两位审稿人的积极态度让我们相当意外，因为我们觉得 Evaluation 做得并不算好，Predicate 定位方法也很是粗糙。接下来的故事，还是由卫佳申同学来讲述：

> 坦白说，对这份临时反复修改的初稿，我们起初并不抱很高期望，更多是抱着听取意见的心态投出。在收到评审意见前，我们继续优化实验、压缩时间成本（将原本 10 天才能跑完的一轮评估压缩到一天多）、修复新发现的细小故障、调整文件结构等等。2026 年 5 月，我们收到三位评审的审稿意见。评审给了我们 rebuttal 的机会，他们建设性的意见也为我们指明了优化方向。我们用一个小规模试点噪声实验回应了评审对人工标注需求的担忧，并逐一回答每个问题，最终获得 minor revision。随后我们补充了完整噪声实验与分析，优化行文逻辑。经过一步步修改完善，我们在 7 月提交了 revision 版本，并最终在 8 月得知最终接收的消息，对此我们倍感荣幸。

## 边界与展望

这篇论文拿到了 Distinguished Paper Award，这大大出乎我们的意料，因为我们自己清楚这个工作的完成度其实并不算高。既然关注比预期多，那我们觉得这个工作的边界更要说清楚。因此，我们会在这里分析一下，这篇论文做到了什么、没做到什么，以及它可能以什么形式影响后续的工作。

### Benchmark

虽然 Benchmark 的构建很不容易，但是这个 Benchmark 本身也存在着一些局限。最明显的就是我们这个 Benchmark 只来源于 Doop，也只覆盖到 Soufflé 语法。此外，由于 Bug 的确认依赖于人工判断，并非所有导致程序行为变化的修改都是 Bug 修复——我们确认 Bug 的方式，说到底就是人工比较相邻版本的差异，而差异只能说明行为变了，说明不了这是在修 Bug。因此，Benchmark 中的部分修改可能来源于开发者对规则语义的主动调整，例如：

* 调整规则传递链并删除已经不再需要的规则；
* 重构已有 Predicate；
* 调整规则接口或数据表示方式；
* 优化分析逻辑以适应新的 Java 特性或依赖版本。

因此，部分被纳入 Benchmark 的故障可能更接近于“错误版本与后续版本语义不一致”，而不完全等价于传统软件工程意义上的 Bug。

### Evaluation

模拟真正开发环境中的故障定位，其实也是一个很难的问题。要做 Fault Localization，首先得有 Testing：得先看到 failure，才谈得上定位 fault。但问题是，在真实的开发过程中，开发者是怎么观测到 wrong facts 的？又会注意到其中哪些？我们没法知道。所以只能用最笨的办法：直接比较 buggy program 和修复版本的 derived facts，只出现在 buggy program 里的 facts 就当作 wrong facts。

这么一来，wrong facts 会非常多——论文里统计过，从几个到几百万个都有，因为最初的 wrong facts 会顺着规则传播、越滚越多——也远比实际开发中开发者可能注意到的多。RQ3 里我们做了抽样，也人为加了一些标错的噪声，结果还算稳健：标注量不用大，效果就接近全部标注。还有一个有点反直觉的发现：抽样的结果偶尔能超过全部标注，因为下游传播出来的那些 wrong facts 反而混进了误导性的证据，少标一点、把这些噪声排除掉，排名反而更干净。

当然，evaluation 里 wrong facts 的分布和真实开发中到底像不像，我们仍然没有答案。不过换个角度想，实际开发中开发者注意到的 wrong facts 本来也不可能是几百万个——人没法靠肉眼盯几百万个 facts，能注意到的也就是分析结果里不对劲的那几个。所以日常开发真用起来，效果说不定比 evaluation 里还好。

存储上我们也做了简化。完整的 proof tree 存不下来——一个 program 跑一遍能产生几千万个 derived facts，每个 fact 的完整 proof tree 都存的话内存根本顶不住——所以我们只记两样东西：每个 fact 由哪条 rule 推出，以及它的直接 parent facts 分别由哪条 rule 推出，proof tree 的其余部分全部丢掉。用这么粗糙的 spectrum，SBFL 的效果居然还不错。不过这套插桩在很大程度上是被 evaluation 的设定逼出来的：evaluation 默认"没被确认为 wrong 的 fact 都是 correct"，于是这几千万个 facts 个个都是 test case，只能边跑边记。现实中大概不会有人这么用：开发者能确认的只有手头这几个 wrong facts，correct 那边抽样确认一部分也就够了，而这些 facts 的 proof tree 事后按需重建就行。

还有一点论文里没展开：一个 fact 可能有多棵不同的 proof tree，不同的 proof tree 会给出不同的 spectrum，定位效果自然也可能不同。Soufflé 实际记录下来的是一条推导路径，我们也就按一棵算，其它的推导路径完全没有利用——这个问题在 Presentation 现场被听众问到了。我之前想过：如果把不同的 proof tree 导出的 spectrum 做并集或交集，其实有点像程序分析里的 over-approximation 和 under-approximation——并集不会漏掉任何可能参与推导的 rule，但会多带进来一些无辜的；交集更聚焦，但可能把真正的 faulty rule 也滤掉。交集和并集大概只是最粗暴的两种玩法，哪种更合适，得交给后续工作了。
